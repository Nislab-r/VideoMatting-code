# 人物渲染流程与多人场景边界

## 已实现的单人物流程

每条任务只有一个 subject_id、asset_path、动作方案和背景配对。一个人物可包含身体、服装、装备及独立骨架的头发；这些对象仍属于一个人物，不等于多个独立人物。

1. **准备与身份检查**：解包素材并重建路径。运行入口对照人物清单核对 ID 和 Blend 路径，只允许清单中的 human 入口。加载原 Blend 后按绑定网格、骨骼语义等选定一套主骨架；保留当前可见服装及头发，修复可定位的贴图路径，不保存修改回源文件。
2. **动作设计**：批量领取任务时使用动作参考的特征和安全动作目录，生成目标人物原生骨架可执行的动作。参考动作不是逐骨旋转复制；目录数量、动作特征数量和计划任务数量分别是不同统计口径。当前展开动作目录有 1,989 个预设，素材有 2,076 个动作参考，计划为 1,908 条任务。
3. **冻结背景配对**：按 sample_id 获取已准备的背景、截取时间及构图位置。检查背景存在、构图与动作索引一致。替换缺失背景后的版本为 background_replacement_v2；任务执行时不临时随机换景。
4. **时序、构图和外观**：按完整动作计算边界及机位，设置全身/半身/头发近景、角度、人物位置、采样、材质与灯光。灯光参考背景统计和已有语义信息；背景本身仍是二维视频，不是重建的三维场景。
5. **完整时序预检**：生成预览并检查动作、末段稳定、几何、肢体、头发及衣物。衣物检查按最终细分条件覆盖完整动作时序；未知骨骼语义或交叉可以阻断任务，不能靠关闭检查直接算通过。
6. **最终前景**：通过预检后生成 1920×1080、30fps 的临时 RGBA16 PNG。核验最终设置、分辨率、PNG 位深、帧数及衣物报告。单帧 smoke 只验证标准入口和一张输出，不能代替整个工作进程的合成验收。
7. **合成与监督**：从 RGBA 提取 16 位灰度 alpha，保留半透明发丝的连续值；背景按 30fps 缩放裁剪到 2K，以 straight alpha 叠加前景。保存 4:4:4 JPEG 合成帧和无损 PNG alpha，并生成 960×540 预览视频。
8. **完成与失败**：检查通过后清理临时工作目录，写入 DONE 并更新队列为 done。已有 DONE 会被信任，因此改设置或改配对后的复现应使用新工作目录。预检/衣物错误会暂停该人物尚未执行的 pending 任务；其他错误记录 failed，不应当作完成。

主要实现：`tools/procedural_render_worker.py`、`tools/procedural_reference_production.py`、`tools/frozen_pairing.py`、`tools/jit_action_designer.py`、`tools/production_quality/`。

## 多个人物依次批量渲染：已实现

每个人物 12 条任务，159 个人物共 1,908 条任务。输出视频仍逐条只包含一个合成人物；背景视频自身可能已经有路人。

先检查各人物适配状态，再逐一调用 activate_subject.py。它只允许原预检为 supported_v6 的入口进入待执行状态；这只是结构门槛，最终动作/衣物检查仍可能失败。脚本没有“一键跳过检查启用全部 159 人”的功能。

```bash
# 先按 config/env.example 设置环境变量；用实际的人物 ID 替换示例。
python scripts/activate_subject.py --subject-id '<first-reviewed-human-id>'
python scripts/activate_subject.py --subject-id '<second-reviewed-human-id>'
python "$DATA_ROOT/tools/procedural_render_worker.py" --worker-id human-0
python scripts/check_progress.py
```

队列通过 SQLite 事务领取任务，同一人物保持串行，不同人物可并行。新版可指定多个 GPU 和每卡槽位，锁按 GPU/槽位区分；参见 [多卡调度](MULTI_GPU.md)。每卡多少并发有效仍需实测，不能直接按卡数或显存倍数折算吞吐量。

默认要求 DATA_ROOT 所在磁盘至少有 180 GiB 可用空间，否则每 300 秒复查一次，可能看起来没有输出。RENDER_MIN_FREE_GB 可覆盖这个门槛，应结合临时 RGBA、预检文件和持续增长的最终输出预留空间；它不是已测得的最低内存要求。

release 队列初始全部为 waiting_release_review；正式服务器的旧运行队列可能有 done、waiting_adapter、paused_motion_redesign 等状态，两者不是同一进度。

## 同一画面出现多个合成人物：尚未实现

现有任务结构没有人物列表、跨人物遮挡关系或实例标签；主骨架选择函数只选择一套主骨架。往同一个 Blend 中放入更多人物、开启多个工作进程、或把多个人物 ID 写成字符串，都不会自动得到正确的多人输出。

如果后续需要多人同镜头，应新增场景级任务，显式记录每个人物的身份、独立动作、起始时间、位置、朝向、尺度和遮挡规则。所有人物必须使用同一机位、时间轴、灯光与 2K 输出设置，并先分别通过现有预检，再检查人物之间的距离、接触、碰撞及完整时序的可见性。

### 可选方案 A：分别渲染，再分层合成（尚未实现）

适用于明确不需要复杂接触、且可给定前后顺序的场景。保留每人的前景 RGB 和 alpha，共用相机标定和时间轴，再按深度从前到后合成。当前脚本会删除临时 RGBA，因此必须先增加前景留存策略及多人合成器。

对于按前后顺序排列的 straight-alpha 图层，第 i 人的可见权重是 `alpha_i × ∏(1-alpha_j)`，其中 j 是其前面的图层；联合 alpha 是 `1-∏(1-alpha_i)`，不能相加后截断，也不能简单取最大值。还应区分独立人物原始 alpha 与被前景人物遮挡后的可见实例 alpha。

整个人物固定排序无法正确处理手臂互相穿插、两人前后关系随空间变化等情况；二维分层也不会自动产生相互阴影或真实接触。只有统一尺度但相机透视不一致的独立前景，不能视为几何一致的多人场景。

### 可选方案 B：同一三维场景联合渲染（尚未实现）

适用于交错遮挡、接触或希望统一几何关系的场景。需要将每个人物资产导入隔离命名空间，处理骨架/材质/约束冲突，为每人绑定独立动作，并增加人物间碰撞检查。联合渲染得到场景前景与联合 alpha；实例监督需要明确可见实例的覆盖贡献及边缘半透明策略，不能直接用不保留透明度的硬 ID 标签替代发丝 alpha。

两种方案都必须新增完整片段验证：时间同步、遮挡顺序、联合 alpha 与实例权重一致性、发丝半透明边缘、人物间穿模，以及输出/元数据一致性。当前仓库没有实现或测试这些多人同镜头能力。

## 当前输出适合什么训练目标

当前长期保存的是合成 RGB、联合单人 alpha、低分辨率预览及报告。适合读取 composite/alpha 的训练流程；没有长期保存独立前景 RGB 或背景帧副本。需要 F、B、alpha 三元组、重新合成或多人分层的训练，应先扩展输出策略，不能从现有 JPEG 合成帧和 alpha 精确还原原始 F/B。

当前二维背景合成不保证人物会被背景中的树、栏杆或路人正确遮挡，也没有重建背景几何后的接触阴影。背景语义与光照匹配有助于外观协调，但不是物理一致性的保证。
