# 多卡调度与每卡并发验证

## 实现范围

发布版工作进程标记为 MULTI_GPU_QUEUE_VERSION=1。可同时使用多张 NVIDIA GPU，每张卡可配置多个工作进程；每条任务仍只渲染一个人物，不能理解为多人同镜头。

每个进程仅看到一个物理 GPU UUID。队列使用 SQLite BEGIN IMMEDIATE 原子领取任务，允许不同人物同时运行；同一人物仍限一条运行任务，避免一个动作预检失败时同人物其他动作已同时投入渲染。GPU 锁按用户、物理 GPU 和槽位区分，多卡不再共用单一渲染锁。CPU 线程默认按进程数量均分，也可显式设置 BLENDER_THREADS。

全量并发上限为各卡槽位之和，但还受可运行人物数、CPU、主机内存、磁盘与 GPU 实测吞吐量限制。增加进程数不保证线性加速。当前不支持跨服务器共享队列：PID 检查、文件锁和路径均按单机设计。

## 检查资源

```bash
python scripts/gpu_inventory.py
```

输出每张卡的编号、UUID、显存总量/占用、利用率和已有计算进程。空闲显存很多不代表 GPU 空闲；其他任务可能已经用满计算资源。多卡启动器和基准工具会拒绝初始时已有计算进程或明显忙碌的卡，不会终止别人的任务。

本次服务器读数是 8 张 A100-SXM4-80GB，全部被其他进程使用，利用率约 99–100%。因此本次没有运行 GPU 并发压测，不能给出经过验证的每卡最优任务数。此前单帧过程中的显存瞬时读数不是峰值，也不能用 80 GB 除以它推算并发上限。

## 多卡启动（需要明确执行，不会自动启动）

先按 FROM_ZERO.md 准备完整工作目录、加载环境变量并启用已审阅人物。下列仅是命令示例，当前维护过程中没有执行：

```bash
# GPU 0、1、2、3，各一个任务槽位
python scripts/render_multi_gpu.py --gpus 0 1 2 3 --slots 1 --start

# 根据实测结果，分别分配 2、1、2、1 个槽位
python scripts/render_multi_gpu.py --gpus 0 1 2 3 --slots 2 1 2 1 --start
python scripts/render_control.py status
```

只选择实际空闲、允许使用的 GPU。未测过的环境以每卡 1 个槽位作为起点，不是已测得的最优配置。省略 --start 会以前台监督进程运行。每卡配置对应 GPU 列表顺序；也可用完整 GPU UUID 代替编号。

运行记录位于 runtime/multi_gpu_launch.json，各工作进程日志在 logs/gpu-卡号-slot-槽位.log，后台监督日志为 logs/multi_gpu_supervisor.log。停止监督进程会向它管理的进程组发送终止信号；不影响未由它启动的其他任务。随后按续跑手册处理被中断的任务，不能删除完成标记。

旧工作目录中的工作进程可能仍是串行版。启动器会拒绝把旧版当作多卡版运行。全新工作目录会复制新版代码；已有实验迁移需先停机、备份代码和数据库、验证任务/设置兼容性，再显式更新工具。仅同步发布文件夹不会修改旧生产目录的 tools 或队列。

## 测量每卡应该开几个任务

先在独占空闲 GPU 上用隔离样例比较 1、2、4 个任务。准备好 FROM_ZERO.md 的 demo 素材目录，使用新的基准结果目录：

```bash
python scripts/benchmark_gpu.py \
  --gpu 0 --assets "$ASSETS_DIR" \
  --video-root /data/videomatting-demo-assets \
  --output /data/benchmarks/gpu0-run1 \
  --concurrency 1 2 4 --repeats 2
```

该工具先执行一次单任务预热，再比较不同并发；每个任务使用独立工作目录，共享只读素材，不使用或修改生产队列。工作负载是随包人物的完整 120 帧动作/衣物检查及一张 2K 前景、alpha 和合成图。

results.json 记录成功状态、整组耗时、每小时完成样例数、采样到的显存峰值和 GPU 平均利用率。显存按整张卡每秒采样，不是精确的进程显存峰值，可能漏掉短时峰值。进程数量是配置值，不能把一个 CPU 预检阶段尚未进入 GPU 的进程当作已经充分占用 GPU。

选择配置时比较吞吐量而不是只看是否装得下：并发翻倍但总耗时也接近翻倍，就几乎没有收益；出现 OOM、输出缺失、衣物检查失败或不稳定时不应继续增加。显存必须留余量，不能贴着卡容量配置。也应监测主机 RAM、CPU 和磁盘吞吐，避免将资源争用误当成渲染算法变慢。

此工具是单一人物的初步基准，不能证明全库安全上限。决定全量配置前，还需要对已适配的高显存人物、复杂头发/衣物及完整视频任务重复测量；不同 GPU 型号或 CPU 分配要分别测量。已有外部任务进入同一 GPU、冷热缓存不一致或输入变化时，结果不可直接比较。

## 本次验证结论

已用隔离 SQLite 队列验证：三个工作进程领取不同人物、任务不重复领取、同人物后续任务保持等待；配置映射与忙碌 GPU 拒绝逻辑也经过测试。GPU 多进程实测和最优并发数仍待空闲资源验证。代码功能、队列测试与真实 GPU 容量结论必须分别记录。

多卡会改变任务领取和首次动作分配的先后顺序，不能保证同一初始模板在不同并发下获得逐项相同的动作选择。复现时应保留已分配的 action_params、动作设计表、事件记录及配置版本，不能只保留并发数。

## 本版强制预检补充

执行前遵循 [人物与任务预检](PREFLIGHT.md)：人物级审计现为可选诊断，默认登记资产可用；生产执行和重试始终由 worker 做任务级完整预检。旧工作目录缺少任务预检 v1 时启动器拒绝运行，需先停机备份并更新 tools，保留原队列、登记表和结果。人物级通过不得替代任务级通过；历史审计标签不再阻止显式启用或重试。
